# Original ONE LOOP: source revision is NOT immutable BRAIN obligation identity

**Incident 12 November 2026, parent [#4198](https://github.com/arthurprinsen-ai/Bedrijfsgeheugen/issues/4198).** Native post source release [#5663](https://github.com/arthurprinsen-ai/Bedrijfsgeheugen/pull/5663) was independently applied as 832nd Supabase migration. However actual original #175 invocation on 11 and 12 November returned `SOURCE_ARCHIVE_RETRY_REQUIRED`, SQLSTATE `P0001`, `OBLIGATION_IDENTITY_IMMUTABLE`. Root cause: `brain_guard_obligation_identity` correctly prevents changing a created `brain_obligations.payload_sha256`; the new original source archiver tried to update this immutable creation hash every time real website/post/SEO data revised the same day's SHA. This triggered a rollback of all seven/eight-class source writes. The base coarse source stage still reported a green cron, which is not an end-to-end proof.

## Permanent fix with same original owners

1. **Producer #175:** immutable creation-time `payload_sha256` is *never updated*. Live source SHA and original ordered manifest are stored as mutable `evidence.source_revision` and `source_manifest`. If source SHA changes, reset the `consumer_ack` to `accepted=false`, preserve previous source SHA, acceptance time and analysis in evidence, increment original version, log each new real SHA in an **append-only dedupe-keyed** `original_daily_growth_source_revision` runtime event. Original obligation key/tenant/day/owner unchanged.
2. **Consumer #140:** independent read of the original daily rows recomputes the same SHA256, requires current source count >= 8, compares to `evidence.source_revision` (not immutable creation hash), still checks immutable `payload_sha256` against the immutable original identity reference, then emits a consumer ACK with exact current revision. CRO/Post experiments remain proposed, not executed or proven.
3. **Heartbeat:** independently hashes the ORIGINAL current source table and requires exact source SHA equal to the current BRAIN revision **and** the same-day original consumer receipt with `accepted=true`. A stale positive ACK between #175 writing new data and #140 accepting it is never trusted. Heartbeat shares the same original event, no second runner.
4. **Live acceptance:** the protected migration must pass Required, CodeQL, Supabase preview and exact GitHub main merge. Then native Supabase migration readback followed by *real* #175 and #140 execution for yesterday/today and fresh Heartbeat readback. No changing trigger, no parallel scheduler, no invented SEO, social metrics, conversion lift or revenue.

Migration: `supabase/migrations/20261112194500_original_growth_source_revision_identity_fix_v1.sql`. Regression `tests/brain-original-source-identity-versioned-ack-20261112.test.mjs`. Original agent rules and machine learning updated.
