# ONE BRAIN portaaldiagnose — geïmporteerde Netlify-code werkelijk livezetten

**Datum:** 31 oktober 2026. **Parent P0:** https://github.com/arthurprinsen-ai/Bedrijfsgeheugen/issues/4198.

De oorspronkelijke Powerhouse-content-loop draaide op Supabase v466 met echte `RED/RECOVERY_DUE`, geverifieerde deadlines en de echte oorzaken voor drie contentkanalen (`CONTENT_GENERATION_BILLING_ACTION_REQUIRED`), Mira (`MIRA_FINAL_MEDIA_PROOF_REQUIRED`) en e-mail (`EMAIL_CANONICAL_AUTHORIZATION_REQUIRED`). De bronaanpassing van `brain/observability/one-loop-guard-diagnostics.mjs` uit PR #5219 stond op main maar de authentieke Netlify-functie `netlify/functions/powerhouse-one-loop-assurance.mjs` importeert deze module **in de gebundelde Netlify-runtime**. De actuele Netlify-productieversie bleef daardoor de eerder gemergede #5216-deploy `6ae5a9432b59433f424c7db6` / commit `873ce9f8271ab277ad4e49a3a11480917acf520b`, omdat de bestaande deploy-applicability deze geïmporteerde source niet als runtime-impact herkende.

**Structurele preventie:** het bestaande `tools/delivery/netlify-deployment-applicability.mjs` classificeert `brain/observability/one-loop-guard-diagnostics.mjs` én `brain/observability/one-loop-assurance-readback.mjs` voortaan als Netlify-runtimecode, met verplichte geauthenticeerde readback. In de **oorspronkelijke** Netlify-handler is de bronafhankelijkheid expliciet gedocumenteerd, zodat deze beveiligde kandidaat precies één normale productiebuild via Git/Netlify triggert. Geen parallelle deployment service, geen direct-to-provider push, geen auth-bypass, geen nieuwe database/agent/scheduler, geen publicatie zonder provider-ID.

**Tests:** `tests/brain-one-brain-guard-netlify-import-impact-20261031.test.mjs` verifieert runtime-impact, fail-closed provider-SHA-verschil, het oorspronkelijke admin-only JWT/tenant-toegangscontract en geen onnodige Netlify-build voor zuivere Supabase-/documentatiewijzigingen. Pas na Required/BRAIN/CodeQL, beveiligde merge, Netlify `ready` op exact nieuw main-SHA én echte geauthenticeerde privé-portaal API-readback mag deze portaal-update als live worden aangemerkt. De publicaties blijven afzonderlijk `RED` tot werkelijk LinkedIn-, Instagram-, e-mail- of blogproviderbewijs bestaat. AI-providertegoed herstellen of een geschorste fallback autoriseren is uitsluitend voor de bevoegde accountbeheerder.
