# GitHub Actions 2026: least-privilege cache token on existing privileged Janitor

Canonical [#4661](https://github.com/arthurprinsen-ai/Bedrijfsgeheugen/issues/4661). Existing workflow is already authorized to reconcile repository issues and collect read-only CI evidence, but the **Janitor job never restores or saves an Actions cache**. Under recent GitHub Actions syntax, `jobs.<job_id>.cache-mode: none` rejects cache restore/write while leaving artifacts, checkout, permission grants and runner behavior intact. Reference: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax and https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching .

This change applies to **only** `.github/workflows/powerhouse-repository-janitor.yml`: a single job-level `cache-mode: none`, no workflow/job fan-out, no new permission grant, no schedule change. Exact JSON telemetry and the existing `powerhouse-repository-janitor-<run>` artifact continue as before. Security rationale: deny unnecessary cache tokens in a write-privileged automation runner and avoid ever restoring untrusted cached executables. Tradeoff: a future Janitor cache consumer would be explicitly prevented from using the cache and must pass security review before any privilege adjustment.

Regression: `node --test tests/brain-janitor-cache-token-isolation-20261023.test.mjs`. Required, CodeQL, native protected merge, main+skill readback, and a genuine new post-merge Janitor provider success required. This does **not** claim better execution time, address four existing GitHub ghost runs, bypass Supabase previews, or close #4661.
