# Powerhouse Problem Radar — canonical intake & routing v1

Date: 2026-09-25  
Fingerprint: `powerhouse-problem-radar-canonical-intake-v1`

## Change

The MKB Probleemradar now has one explicit machine-readable standard for every new or changed Dutch MKB signal:

`SOURCE -> EVIDENCE -> DEDUPE -> PH-Pxxx -> PROBLEM RADAR -> CUSTOMER INTELLIGENCE -> OPPORTUNITY/CONTENT -> OUTCOME -> LEARNING`.

Accepted evidence may never end as an isolated research note or content idea. It is stored once with provenance/freshness/confidence, mapped to an existing canonical `PH-Pxxx` when possible, and becomes reusable by the executive cockpit, evidence drawer, opportunity intelligence and governed content pipeline.

## Customer portal rule

External evidence is context or benchmark evidence, not proof that a specific customer has the problem. A portal projection therefore requires tenant relevance or tenant evidence and keeps impact classified as `OBSERVED`, `ESTIMATED` or `POTENTIAL`. The cockpit stays limited to the five highest-priority directieproblemen and exposes the underlying evidence through “Waarom zegt Powerhouse dit?”.

## Content rule

The same canonical evidence lineage may create blog and LinkedIn-company candidates using:

`probleem -> symptomen -> zakelijke impact -> oorzaak/data -> praktische aanpak -> Powerhouse-functionaliteit -> meetbaar resultaat -> CTA`.

Duplicate angles are blocked and publication is not terminal before provider readback.

## Permanent prevention

- map to the existing Problem Library before creating any candidate;
- preserve recurrence without duplicating canonical evidence rows;
- never fabricate numbers;
- never turn qualitative entrepreneur signals into prevalence statistics;
- refresh current claims before use;
- never promote policy proposals to current law without verification;
- never call realized value without Verified Value evidence.
