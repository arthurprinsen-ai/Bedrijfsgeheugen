## Production observation and root cause

Direct original Supabase readback shows **14** canonical innovation candidates, **14** native `INNOVATION_INTAKE` all **PLANNED**, and **14** original `INNOVATION_DELIVERY` obligations all **OPEN**. Only one original intake has an independently released original engineering PR, one has a source-bound no-change review, and none has verified consumer ACK or proven customer benefit. The existing code-writer selected no new safe source-bound code candidate after those two.

The **nine** generic `bounded_learning_followup` candidates were not empty: all nine map exactly via `candidate.baseline.quality_fingerprint` to original `public.powerhouse_quality_events`. Those original quality records contain historical guarded/verified statuses, regressions and alleged release references; some have recent changes, others date from September. An historical quality status is **not** independent proof that the original innovation is now producing verified production benefit. The earlier implementation failed to move these original observations into the **same** 14 original Brain operations; the engineering agent therefore saw generic baseline-design tasks forever. One original CRO task remains at event definitions/consent/holdout due, and four are concrete engineering tasks (one published, one no-change review, others requiring reconciliation of existing releases).

## Bounded repair in the existing daily engine

In the SAME `.github/workflows/powerhouse-daily-self-evolution.yml` job, before the existing code-candidate selection, run `scripts/brain/innovation-original-evidence-reconciliation.mjs --writeback` with the already-authorized Supabase service role. No new schedule, queue, table, agent, sender, parallel database or direct production effect.

The script uses the pre-existing `readCanonicalRows` exact-count source, extended read-only to original baseline and expected impact. It obtains **only the nine original matching quality events** via source-bound exact-count, source fingerprint, original component, owner and original revision checks. Every one of the fourteen original operations gets a deterministic, nonterminal `original_evidence_reconciliation` envelope with the exact source SHA/revision, original owner and action decision, original qualitative evidence digest, original metric hypothesis digest, and a **source-appropriate next verification action**. The original quality event raw performance data is hashed, not copied into agent prompts or GitHub artifacts. For previously built or no-change tasks, original receipts are preserved and the remaining **actual effect/consumer** work is named explicitly.

The stage has a deterministic fingerprint: same-source daily replay is a no-op; a verified new source-quality revision creates a new source-bound evaluation envelope. Writes go ONLY through the original `brain_transition_operation` version-CAS and independent second `brain_operations` GET; source/version conflicts fail closed and do not overwrite other agents' work.

Crucially the plan cannot authorize provider dispatch, fabricating effect measurements, closing any original task, changing tenant privacy, or asserting terminal success. Actual code PR and deployment remain subject to the original pinned sandbox, protected Required/CodeQL, exact Netlify production SHA, independent provider readback, real treatment/baseline measurement and ONE BRAIN applied learning.

## Verification and prevention

Regression suite `tests/brain-innovation-original-evidence-reconciliation-20261117.test.mjs` covers exact original source and SHA, duplicate quality fingerprint, missing source, modified original owner, COP/quality guards, stale versus new quality evidence, no false completion, CRO holdout and original version-CAS plus independent provider readback. The existing automation Required lane now executes this suite, and the existing daily job rechecks the source evidence before code authoring.

This is a **reconciliation and current-evaluation gate**, not proof that nine generic suggestions were implemented or that fourteen business benefits exist. An unverified or stale historical claim remains an actionable debt and must go through the original owner and release. Continue source-informed engineering/measurements one-by-one after the existing protected code builder receives a concrete, safely reviewed work package.
